# Domainry Knowledge UI design contract

## Identity

Domainry Knowledge is a calm editorial operations workspace: dense enough for long-running knowledge maintenance, but visually quiet enough that the document remains the primary object. The package is product-neutral: an embedding product supplies semantic colors, while standalone mode uses Domainry defaults.

Evidence: the current knowledge/library workflows, the page tree, permissions and publishing states, multi-user editing visibility, the existing `KnowledgeWorkspace` package boundary, and Verdent Deck's light/dark semantic token system. Verdent is a host, not a color dependency of this package.

Attributes: precise, editorial, trustworthy, collaborative, restrained. Non-goals: consumer-style oversized cards, decorative gradients, pill-shaped controls everywhere, hiding operational state behind color alone, and nested bordered cards that repeat the same grouping.

## Color roles

Components may consume only the following `--knowledge-*` roles; literal product colors belong in the light/dark default token declarations or in user-authored content palettes.

- Backgrounds: `canvas`, `surface`, `surface-elevated`, `surface-subtle`, `surface-tint`, `surface-hover`, `surface-active`, `input`, `overlay`.
- Text: `text`, `muted`, `faint`, `on-accent`, `link`, `code-text`.
- Boundaries: `border`, `border-strong`, `focus`, `selection`, `shadow-sm`, `shadow-md`, `shadow-lg`.
- Actions: `primary`, `primary-hover`, `primary-active`, `primary-soft`.
- Status: `success`, `info`, `warning`, `danger` plus matching `*-soft` and `*-border` roles. Status is never communicated by color alone.
- Authored content: presentation themes, whiteboard strokes, mind-map themes, charts and collaborator identity palettes remain explicit data colors; they do not style application chrome.

Standalone defaults provide complete light and dark values. The root uses `data-knowledge-theme="light|dark"` and `color-scheme` follows that resolved value. Host products override semantic variables at the root; no Domainry component imports a host token package.

### Verdent host mapping contract

| Domainry role | Verdent Deck semantic owner |
| --- | --- |
| `canvas` | `background.deck-background` |
| `surface` / `surface-elevated` / `input` | `background.deck-module-background` / `background.deck-overlay-modal` / `background.chat-background` |
| `surface-subtle` / `surface-hover` / `surface-active` | clear black/white layers for the resolved theme |
| `text` / `muted` / `faint` | `black.clear.100-85` / `65` / `45` |
| `border` / `border-strong` | `border.clear-10-6` / `border.clear-15-10` |
| `primary` / hover / active | `button.solid.brand` / `brand-hover` / `brand-active` |
| success / info / warning / danger | matching `status.*` tokens |

The mapping is implemented by the Verdent product shell, not copied into this package. Runtime host preference changes update the root attributes and variables without remounting the editor.

## Typography

- UI: `Inter`, `-apple-system`, `BlinkMacSystemFont`, `Segoe UI`, `PingFang SC`, `Microsoft YaHei`, sans-serif.
- Editing: `SFMono-Regular`, `Cascadia Code`, `Menlo`, monospace.
- Page title 26/32, section title 15/22, body 14/24, label 12/18 semibold, metadata 12/18.
- Mixed Chinese/Latin copy must wrap naturally. Revisions, block counts and clocks use tabular numbers.

## Geometry and rhythm

- Spacing scale: 4, 8, 12, 16, 24, 32.
- Radius scale: 6 for controls, 10 for panels, 14 for overlays. Avatars and compact statuses may be circular.
- One-pixel dividers own hierarchy; shadows are reserved for the document canvas and overlays.
- Icons are 14–18px with consistent Lucide strokes.

## Layout and responsiveness

- Authentication uses a two-region editorial entry shell on wide screens: a quiet product-led knowledge preview and value statement on the left, and one focused white form surface on the right. It must not present a small floating card inside an otherwise empty decorative canvas. Below 900px the product preview yields to the form, with a compact brand lockup retained above the heading.
- Desktop page workspace: 260px navigation and a flexible document or native-editor canvas. Collaboration detail is an on-demand popover from the page header; it never reserves a permanent content column.
- Every selected-page mode uses the full width available to the right of the knowledge tree. Title, utility toolbar, reading surface, editor, history and auxiliary mode surfaces share one stable outer boundary, so changing modes never recenters or changes the workspace width. Prose keeps comfortable inner padding instead of a different outer container width; native editors retain their own internal stage or inspector layout.
- The product shell owns the outer boundary. The actual left navigation rail starts with one compact page filter and a two-tab switcher for Knowledge bases and Quick. Knowledge bases is the default tab and lists every accessible library with the same row and disclosure treatment; expanding one library shows its page tree. The disclosure arrow exclusively expands or collapses, while clicking the library identity selects that library root as the creation target. Clicking a page selects that page as the creation target. Uploaded file pages use the filename to render a format-specific icon (PDF, Word, presentation, spreadsheet, image, audio, video, text, or generic file) everywhere the page appears. Quick is a flat list of pinned pages rather than a fake expandable directory. Personal and Team are not navigation or data-model concepts: every library is collaborative, and a one-person library is simply a library whose only member is its creator. Recycle Bin is not persistent navigation; managers open it from the current library's settings. Recent visits is intentionally absent because it duplicates retrieval history without expressing durable information architecture. The filter query stays stable while switching libraries and filters the active tab without moving or duplicating the control. There is no All root, Collection root, personal/team split, team-library select, recent-visits root, recycle-bin root, or second permanent navigation rail. The toolbar owns exactly one icon-only creation menu immediately before library settings; its menu clearly separates “Add knowledge base” from document types and file upload. Knowledge-base rows contain disclosure and identity only, and no detached “New” row or additional plus control is allowed. Creating a library with no additional member produces a valid one-person collaborative library, while adding members or organizations changes access rather than the library's visual category. Full-text search may still be mounted once in a host-owned title bar; it is a retrieval workflow and must remain visually distinct from the compact page-tree filter. Embedded hosts that already provide that retrieval path may disable it, in which case no empty top row or hidden keyboard shortcut remains. The account is represented by a compact avatar icon. Search results replace the content surface without repeating the input in the page title or results heading. Sources, members, recycle bin and library metadata belong to one manager-only dialog. Header actions such as Export and Edit share the same 36px control height, padding, radius and type scale.
- Knowledge libraries are first-class nested tree nodes, not options in a select control. Backend ownership details may determine permissions, but they must not produce separate personal and team navigation branches.
- The document surface fills the selected-page workspace; readable line length is managed by content padding and editor typography rather than a narrower, independently centered shell.
- Below 720px the page tree becomes a bounded top region and actions wrap by priority. Collaboration and suggestion detail remain on-demand overlays rather than becoming permanent document columns.
- Controls have at least 36px desktop height and 42px touch height.

## Component contracts

- Authentication forms use explicit labels, leading field icons, visible focus rings, a password visibility control and one full-width primary submit action. Loading and errors occupy the form flow rather than shifting the shell. The auth shell may illustrate existing search, collaboration and publishing capabilities, but must not imply unauthenticated access to workspace data or add unavailable recovery/SSO actions.
- The signed-in product header keeps identity text quiet and uses a compact icon-only logout action with an accessible name and hover title; logout must not compete with the workspace's primary actions.
- Navigation rows are flat, not cards. Selection uses a subtle fill, semantic text color and explicit text weight without a second left-edge accent stripe.
- Quick is a compact navigation tab backed by the shortcut page-state collection. It exposes explicit loading, empty and pagination states without creating a second page-list region. Shortcut is the only personal page-state toggle exposed in the page toolbar; favorite and subscribe are intentionally absent because they duplicate Quick and notification workflows without adding a distinct navigation model. Recycle Bin is a library-settings section containing archived pages and restore actions; restore returns the same stable page identity.
- The selected page header uses two deliberate rows: a large title with classification, followed by one unbroken metadata row containing version summary, owner and review state. Entering body edit mode must not turn the title into a form field; the title keeps its display typography and becomes a visually unboxed input only after an explicit double-click. Long titles may wrap, but the classification badge is a fixed, non-wrapping label and must never be squeezed into a taller shape. The current page must not be repeated as a separate breadcrumb above the title; only actual ancestors may appear inline before it. Presence stays aligned to the header's right edge. Document export, print and format conversion remain editor-owned but render in the header action row beside Edit, so the action never moves when switching page modes. Native workbench formats keep their specialized export controls in their own toolbars. Narrow layouts may scroll the metadata row instead of splitting each field onto another line.
- Shared page metadata belongs to the stable page identity, not to one draft or published version. The page header summarizes status, owner, review time and tags; the compact page-properties view edits those fields plus typed custom properties. Unsaved header projections must say “未保存”, owners and person properties resolve only current library members, and metadata revision/CAS remains independent from page content revisions.
- Page references and backlinks are projections of the server-owned normalized reference graph, never a browser scan or copied-title list. “引用了谁” keeps an unavailable tombstone when the target is archived or no longer authorized, but exposes no target title or type; “被谁引用” omits every source page the current user cannot read. Visible titles and content types resolve from each page's current authorized projection, so rename, publish and ACL changes take effect without rewriting source blocks. Both directions paginate by opaque cursors and retain stable page and Block IDs for navigation.
- Knowledge-tree rows are selected by clicking anywhere on the entry label and reordered by direct drag. The upper and lower edge indicate sibling insertion; the center indicates nesting under that entry. Persistent up/down action arrows are forbidden because they duplicate the spatial drag model. Filtering and archived views do not expose partial-list sibling reordering.
- Disclosure chevrons belong only to branch nodes. Once a node's child list is resolved as empty, the glyph disappears while an equal-width spacer preserves title alignment; creating, moving or removing the last child refreshes this state from the server.
- One boundary owns each section. Child rows use spacing and restrained surface contrast; repeated full-width rules are avoided when whitespace already expresses the grouping. Upload drop zones, document previews, protected confirmations and dialogs are the only ordinary nested surfaces.
- View modes inside a selected knowledge entry use a compact tab strip for reading, editing, suggestions, history and comments; mutations such as publish remain visually separate. Activity is intentionally absent because it repeats information already available in history and comments.
- The everyday page toolbar exposes in-page search, Quick, and outline after the primary page modes. Its overflow is intentionally limited to page permissions, controlled sharing, and archive/restore. AI writing, page governance, move, metadata, references, relationships, permission analysis, duplicate, favorite, and subscribe are not toolbar or overflow-menu entries.
- Page permissions, controlled sharing and page governance use one management-panel contract beside the document: identical width, heading hierarchy, field density and action spacing. Opening a panel divides the already full-width content row into a flexible document column and a fixed management column with one standard gutter; it must not recenter or shrink the document inside the flexible column. Governance must not fall below the document, and every identity-result popover remains anchored to its own search field. The title and utility toolbar always retain the same full workspace boundary. Internal ACL revisions and a healthy remote-projection acknowledgement are not user-facing status; normal success stays quiet after the save notice.
- Suggestion mode is a review workflow, not a second editor: the draft stays read-only and keeps the full document measure, a compact mode bar states that only whole-block insertion or deletion is supported, and selecting content opens an on-demand suggestion drawer. Pending suggestions never reserve a permanent right column, and an unavailable anchor never leaves a disabled form occupying the page.
- Comments project every valid Block anchor back onto the original line with a persistent warning-toned mark and compact thread count. Selecting either the source marker or quoted anchor activates the same thread in a non-modal right drawer; while that drawer is open, the document uses the remaining readable measure instead of being covered or becoming a permanent two-column layout. The drawer uses the product UI font stack with a 15/22 title, 13/20 comment and composer text, 12/18 labels, and 10/15 metadata; native textarea defaults must never leak into this surface. Resolved anchors stay visible but muted, while changed or deleted anchors remain explicitly invalid only in the drawer. Comment actions stay limited to reply, edit, resolve and delete; the drawer neither creates nor displays page tasks.
- Publishing is one explicit action after draft synchronization. The everyday editor does not ask for a release note; version history shows author, time and content summary without an empty “no release note” placeholder.
- History uses the same full workspace boundary as every other page mode. Immutable published snapshots are the default history view and expose preview, comparison and rollback-to-new-draft actions; high-volume Block edit records live behind a separate audit tab and must never push rollback below the fold. Rollback creates a new draft revision and never rewrites a published version.
- Backend resource types must not become primary navigation by default. Native documents and imported files appear as individual knowledge entries inside the content rail; upload remains an action in the create menu, never a second permanent navigation row. Library settings use a stable section rail for basic information, member access, data and indexing, recycle bin, and dangerous operations; Enterprise does not expose external-source binding in this surface. Member and organization roles always read and write the currently selected library, and the section heading names that library so it cannot be mistaken for a global workspace ACL. The low-level original-document inventory is named “Ingested files”, appears only under Data and indexing for managers, explains its recovery/diagnostic purpose, and never offers the normal upload journey. Its background status refresh is silent, runs only while an item is actively processing, and stops once every visible item reaches a stable or actionable state; it must never flash the entire section back to a loading placeholder on a timer. Membership, recycle bin and library metadata remain distinct settings sections instead of one continuous form. Library archive/restore belongs only to Dangerous operations; page restore belongs only to Recycle Bin. Neither shares the save row with ordinary metadata. The selected library must not repeat a large title/description header when its scope is already clear from the surrounding navigation. Management sections rely on headings, whitespace and subtle group surfaces instead of stacking dividers at the section, list and row levels.
- The create trigger opens a type menu for document, multidimensional table, spreadsheet, presentation, form, mind note, whiteboard, mind map, flowchart, and upload/import. Choosing a native type immediately creates a typed child under the selected entry, selects it, opens the matching editor, and focuses its title; there is no intermediate create form above the tree. Upload/import opens the file picker and the completed file itself becomes the entry. A page's `content_type` is immutable after creation, its structured content is versioned through the same draft/publish/history chain, and the server derives searchable plain text from the typed payload. Editable titles support explicit edit mode and the desktop convention of double-clicking the title.
- File selection is a one-step action. Choosing image, video, audio, file, attachment, import, or replace opens the native file picker in the same gesture; it must not first create an empty block or open an intermediate upload panel. The create menu offers multi-file selection and recursive folder selection. Folder paths are display context for the upload queue; selected files are flattened under the tree node that was selected when the picker opened, without synthesizing folder pages. Uploads run sequentially through a visible bounded queue that reports hashing, chunk transfer, page creation, completion and per-file failure. The application materializes each file page only after its original has uploaded successfully, so cancelling or failing the picker leaves no empty placeholder behind. Dialogs remain only when the workflow requires metadata or explicit destructive confirmation.
- Code blocks use the product's quiet light-gray editorial surface, a slightly stronger toolbar divider, and the light syntax palette; they do not introduce a detached dark theme into the document. Choosing a block or inline formula opens one focused LaTeX input with live preview and writes content only after confirmation, never by inserting an empty upload-like placeholder first.
- A callout exposes one semantic tone control, not separate icon and tone fields. Its icon communicates the current Information, Success, Reminder or Warning state and cycles to the next state when clicked. Page-header Export and Edit actions use the same exact control box, icon size and type scale.
- A file entry is a normal `file` page under the selected tree node, never a second document list. Its canonical page body stores only `document_id`, `display_mode`, and a display title; the immutable original, scan state, parsed content, index lifecycle, preview bytes, and download authorization remain owned by `KnowledgeDocument`. The page display title remains renameable without entering a body editor or mutating the original filename. The UI resolves that reference on every open, shows a compact original-file status strip above the inline preview, and names the primary retrieval action “Download original file” rather than the ambiguous “Export”. It renders an explicit unavailable state after deletion, quarantine, scan failure, or revoked access and never persists a download URL in page content.
- PDF preview is one continuous vertical reading surface. Only the current page and its immediate neighbours retain rendered canvases; distant pages keep stable placeholders so long documents remain bounded in memory and do not jump while scrolling. A persistent translucent toolbar stays fixed at the bottom of the reading viewport with page jump, zoom, download, print, and fullscreen actions; its previous and next buttons are navigation shortcuts inside the continuous document, not a click-to-turn rendering model. Presentation files retain slide-oriented navigation because slides are discrete authored units.
- Native knowledge entries are rendered through a content-type editor registry rather than one handwritten conditional component. Document and mind-note surfaces use BlockNote; multidimensional tables use AG Grid Community; spreadsheets use Univer Sheets; presentations use a Knowledge-owned 16:9 slide model and editor with PptxGenJS only as an export adapter; whiteboards use an Excalidraw-backed canvas; forms use the Form.io builder; mind maps use Mind Elixir; flowcharts use LogicFlow. Every engine is loaded only when its content type is selected and is wrapped by the same title, draft, publish, history and permission shell.
- Uploaded file pages preview the authorized original with a renderer selected by file type: PDF uses paged canvas rendering, PPTX preserves slide layout through an in-browser PowerPoint renderer, images use the browser image decoder, audio and video use native media controls, DOCX and spreadsheet files use their dedicated readers, and text/source formats remain selectable text. Video preview chrome uses a neutral dark media surface; product green is reserved for actions and selection state, not posterless video fill. A successful upload is never represented as a synthetic text-only substitute for the original file.
- `PageTypeDefinition` is the only frontend registration point for a page type: stable ID, capability bits, icon, labels, native create action, lazy editor, read-only renderer, preview renderer and importer are declared together. The workbench tree, create menu and `KnowledgeEditor` consume that registry; they do not carry parallel type switches. `BlockDefinition` performs the same job for BlockNote specs, Slash entries, read-only rendering ownership, server-validator IDs, text-extraction keys and required capabilities. Both registries reject duplicate or incomplete definitions during module initialization.
- Page and Block implementations are compile-time trusted code only. Stored content can select only a registered stable type; it cannot provide a component, script, HTML renderer, iframe or dynamic plugin. The server independently resolves its code-owned page/Block definitions, validates canonical content, extracts search text and references, and runs publish checks before creating an immutable version.
- Rich documents persist one canonical Block JSON tree; BlockNote binds that tree to a Y.Doc and Yjs merges block structure plus rich-text nodes. Daily edits carry a batched Yjs delta and canonical Block JSON produced from the same editor state; a full Yjs state is included only when the server-declared count or byte checkpoint threshold is due. The server serializes update clocks, validates the Block schema and content hash, keeps a bounded delta log, stores gzip checkpoints, and rejects stale writes so the client must merge and retry. Other native editor types persist their own typed JSON snapshot through whole-draft optimistic concurrency. Editor adapters may additionally receive the document collaboration binding, while third-party chrome is themed through Domainry semantic tokens rather than introducing a second visual system.
- Collaboration transport is an adapter boundary around `connect`, `sync`, ordered `stream`, `close`, and `publish`; canonical Block JSON, Y.Doc ownership, session IDs, server clocks, update IDs, checkpoints, ACL and immutable publishing do not depend on whether the adapter uses POST + SSE or WebSocket.
- POST + SSE remains the production transport until a controlled load test proves at least one unmet requirement after ordinary batching and gateway tuning: p95 durable edit latency above 250 ms for 15 minutes, more than 10 accepted update batches per user per second for high-frequency tools, p95 binary delta above 64 KiB with measured base64/HTTP overhead above 20%, more than 10,000 active streams per instance exceeding its file-descriptor or memory budget, or more than one transport reconnect per active session-hour caused by the SSE path. A WebSocket adapter must reuse the same session, clock, update-log, checkpoint, revocation and publish contracts; it may not introduce another content protocol.
- External clipboard content is an import boundary: BlockNote-owned clipboard payloads and authorized files keep their native handlers, Markdown and plain text are routed explicitly, and external or Office HTML is allowlist-sanitized before parsing. Block JSON, Markdown and printable PDF are read-only projections of the current editor state and never replace canonical Block JSON.
- Slash suggestions are derived from the trusted Block and Page Type registries. The default surface is a compact single-column anchored menu; it expands to a second column only while a real submenu is open, never reserving an empty pane. A submenu title is one global root entry even when its registered items come from different source groups; repeated or non-contiguous group labels are merged in first-seen order. Its height is bounded so the document remains visible behind it. Grouping, search, nested presentation, hover/keyboard state, and bounded local recents are UI-only; permission and capability checks remain live, and disabled choices explain their missing capability.
- Forms use aligned label/control rows on wide screens and one column on narrow screens. A form section has no extra card when its parent already owns the work surface.
- Browser-native inputs keep native semantics but not native chrome: every repository-owned select uses the shared Ariakit-backed `Select` primitive with a portaled, collision-aware product popover; its hidden native select is only the form/change-event bridge. Page-local visible `<select>` controls are forbidden. Checkboxes use the brand selection state, file inputs are represented by labelled product controls, and scroll regions share one restrained scrollbar treatment.
- Dialogs use one outer overlay surface; their headers, toolbars and content are divided regions rather than additional cards.
- The editor canvas owns the main elevation. Toolbars are divided regions inside it, not nested cards.
- Presence uses overlapping avatars plus an explicit online count. Opening that compact control shows one row per user with the current block, unique edited-block count and last heartbeat, without narrowing the editor.
- Connection, merge and publish states always include text and an icon; collaborator colors never encode success or failure.
- Permission and conflict notices use semantic bordered callouts, not generic cards.
- Success and informational feedback uses one compact bottom-right toast and clears after two seconds. It never reserves layout space or becomes a full-width banner. Errors and warnings stay in the operation flow until the user resolves the underlying state.

## Motion and accessibility

- Feedback transitions are 120–180ms and limited to color, border and opacity.
- `prefers-reduced-motion` disables nonessential transitions and spinners.
- Every interactive element exposes a keyboard focus ring. Selected/online/conflict states have textual equivalents.
